Why not just let the agent click by pixels?

Browser automation tools see the DOM from the outside. reins lets your app declare a small, stable contract from the inside—and pairs cleanly with Playwright when you want both.

Reaching a screen state (e.g. Arabic + logged in + 3 cart items) Clicks through 6 screens, types passwords, waits on spinners, breaks when copy changes. Runs registered page tools if the browser supports navigator.modelContext. One reins_run_action call with schema-validated JSON input. Also registers on WebMCP automatically.

Install the single npm package + MCP server

Prefer to wire it by hand? Install reins once and add npx reins bridge to your project's .mcp.json:

npm i -D @mindmakr/reins
{
  "mcpServers": {
    "reins": { "command": "npx", "args": ["reins", "bridge"] }
  }
}

1. Bundler plugin & dev connect vite.config.ts + src/main.tsx

// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import reins from '@mindmakr/reins/vite';

export default defineConfig({ plugins: [reins(), react()] });

// src/main.tsx
import { reins } from '@mindmakr/reins';
import { zustand } from '@mindmakr/reins/adapters';
import { useAppStore } from './store';

if (import.meta.env.DEV) {
  reins.state('app', zustand(useAppStore));
  reins.connect();
}

Build script gate: "build": "vite build && reins verify dist"

2. Register actions & panels src/Settings.tsx

import { useReinsAction, ReinsPanel } from '@mindmakr/reins/react';

export function Settings() {
  const { setLocale } = useI18n();
  useReinsAction({
    name: 'set-locale',
    description: 'Switch the UI language',
    input: {
      type: 'object',
      properties: { locale: { type: 'string', enum: ['en', 'ar', 'fr'] } },
      required: ['locale'],
    },
    run: ({ locale }) => setLocale(locale),
  });
  return <ReinsPanel id="settings">…</ReinsPanel>;
}

Also exposes window.__reins__ in browser DevTools and registers WebMCP tools when paired.

Twelve MCP tools. Seven hard security limits.

Give agents instruments across frontend and backend, plus shareable Markdown session reports—with boundaries enforced in code, not just prompts.

The 12 MCP tools

  • reins_list_actionsReturns the paired app and any paired @mindmakr/reins/node servers, registered actions with JSON schemas, state sources and mounted panels. Always call this first.
  • reins_run_actionRuns one named action on the app or server: { name, input, confirm?, target? }. Also records a [reins] <name> performance measure.
  • reins_stateReads a redacted snapshot of one state source (Zustand, Redux, React Query, route, storage) or all of them.
  • reins_networkRecent fetch calls: method, URL, status, startMs, duration in ms, traceId, and redacted headers/bodies.
  • reins_errorsRecent console.error calls, uncaught exceptions and unhandled promise rejections.
  • reins_panel_boxBounding box of a <ReinsPanel id> in CSS pixels with devicePixelRatio and viewport dimensions.
  • reins_snapSaves a pixel-exact PNG of a panel to .reins/snaps/ (via Playwright CDP in browsers or adb screencap on Android).
  • reins_perfPage lifecycle timings (TTFB, FCP, DOM interactive, load), component/panel mount times and render counts, API call latency stats, and a unified millisecond timeline with server spans joined by x-reins-trace.
  • reins_domInspects a panel or CSS selector's DOM subtree, bounding boxes, computed CSS styles (direction, display, flexDirection, overflowX), and automatic layout issue flags (horizontal-clip, vertical-clip, zero-size).
  • reins_serverWhen paired via @mindmakr/reins/node: inbound requests with dbMs and spans (catches N+1 queries), outbound upstream fetches, slowest routes, and Node event-loop lag (p50/p99/max) and memory.
  • reins_reportSaves .reins/sessions/<time>-<slug>.md and .json with automatic plain-language findings; diff before/after fixes with npx reins report --compare, or let testers export via @mindmakr/reins/record (?reins=record).
  • reins_flightRead only, needs no paired app: the flight report from a saved report file or the file store under the project, as Markdown and data. Process keys only when asked.

Security model (enforced in code)

  1. No development reins in production. Core turns on only in dev builds. Bundler plugins alias reins to @mindmakr/reins/stub, and reins verify fails the build if __REINS_DEV_ONLY__ is found.
  2. Off until paired. Before the bridge accepts its 192-bit token from .reins/token, reins patches nothing and adds no listeners.
  3. Loopback & origin locked. The bridge binds to 127.0.0.1 only (no host flag) and refuses non-localhost WebSocket Origin headers.
  4. Redacted by default. Request/response bodies, Authorization/Cookie headers, storage values and sensitive state keys (token, password, secret, session) become [redacted] unless allowlisted.
  5. Consequential actions require confirmation. Any action marked consequential: true is refused unless called with confirm: true.
  6. Full audit log. Every pairing, refusal, MCP call, DevTools call and WebMCP call is written to .reins/audit.log with redacted arguments.
  7. Lazy & no eval. Waits for load + idle before pairing, and can only run functions explicitly registered by the app.

Flight: report-only checks on a production server.

Production builds contain no development reins. The flight entry, @mindmakr/reins/flight, is the only part of reins meant for production. It records the steps of a server's long-running work, checks them against the promises in reins.flight.json, and reports what it finds. It never retries, restarts, rolls back or blocks anything.

What it does

  • flight.step(process, key, step)Records that one run of a process (a payout, an import) reached a step. Returns at once and never throws.
  • within · once · order · endsThe four promise kinds, each with a why a person approved, checked over a look-back window. flight.probe(id, fn) adds checks on the app's own data.
  • blind · basic · broken · drifting · unusualThe five kinds of finding, sent to a signed webhook, a file or a function, at most 5 an hour per sink. Basics such as failed or slow requests need no manifest.
  • memory · file · PostgresThe stores. Postgres goes through the app's own query function, so reins adds no driver; flight ships the table definition for the app's own migration.
  • flight.report()The report data, with Markdown and script-free HTML renderers to show behind the app's own sign-in. reins flight report --compare shows which findings a fix resolved.
  • No actions · no pairing · no portA request is kept as method, route pattern, status and timing only. Each safety rule has a test, listed in SECURITY.md.

Add it to a server

Install it as a regular dependency, because it runs in production:

npm i @mindmakr/reins

Start it once, add the hook, and record the steps. The config module holds the store and the sinks, read from the environment:

import { flight } from '@mindmakr/reins/flight';
import config from './flight.config.mjs';

flight.start(config);
app.use(flight.middleware());
flight.step('payout', payout.id, 'bank.sent');
npx reins flight check
npx reins flight report --config flight.config.mjs
npx reins flight watch --config flight.config.mjs

Or let your agent do it: /reins:flight proposes the processes and promises in plain words and wires nothing until you approve them.

What flight does not protect against

  • A secret in a step name or process key.Flight keeps both as given. Never build them from personal data or secrets.
  • A store or report page shown without sign-in.The store and the report JSON hold process keys. Show the report only behind the app's own sign-in, and keep the store private.
  • A webhook address that points somewhere it should not.Flight sends to the address the app gives it. Read it from the environment and check where it goes.
  • Anyone who already controls the server.They can change the app, its config module or flight itself.

These limits and flight's safety rules are in SECURITY.md: what flight does not protect against.

Built for Lucid Coding

The companion to Coordinator

Coordinator (mindmakr/coordinator) runs multi-step engineering work through builders and independent blind critics until every behaviour meets a hard bar. reins gives those builders and blind visual critics hands and eyes inside your running app.

  • 1. Agree the bar before the build (Principle #3). Coordinator writes each unit's bar as testable given / when / then behaviours referencing your app's reins actions and <ReinsPanel id> names.
  • 2. Give agents instruments, not just screenshots (Principle #2). The builder and critic read reins_state, reins_network, reins_perf (lifecycle, component mounts & render counts, API latency timeline), and reins_dom (computed CSS & overflow clipping flags) alongside reins_snap PNGs.
  • 3. Blind critic & measurement on the record (Principles #4, #5 & #8). A separate visual critic—who never sees the builder's reasoning—drives your app across locales (e.g. en and ar RTL), verifies zero layout clipping and fast paint/mount timings, and attaches durable proof on the Coordinator dashboard.
